# ADR 0019: Generated-file provenance is opt-in, per-project, and ownership-scoped

**Status:** Accepted (2026-09-25, Architect ruling for #1885).
**Source issue:** #1885 — identify which TangleClaw project generated a file without claiming
ownership of user content or creating repository churn.
**Builds on:** ADR 0001 (one shared predicate for paired state), ADR 0013 (a setting takes effect or
says why not), and #1619 (committed carriers contain no per-checkout identity).

---

## Context

Several TangleClaw-generated files move between projects or appear outside the UI that created them.
Their origin is then difficult to identify. A small generated comment can preserve that provenance,
but a generic "stamp every file we write" rule would be unsafe: some files are user-owned, some
contain only a TangleClaw-managed block, some formats do not support comments, and existing marker
text is machine-read as permission to replace an entire file.

In particular, `Generated by TangleClaw` in the first three lines of an engine carrier is a
load-bearing ownership marker. The new feature must never manufacture, move, obscure or imitate
that marker. Provenance describes origin; it does not grant write authority.

## Decision

### 1. The setting is per-project and off by default

`provenanceWatermark: { enabled, template }` lives in project configuration. Missing configuration
resolves to `enabled: false`; a missing, null or empty template resolves to the shipped default. The
first release has no global override. A future global default may be proposed separately, but it
must preserve a project's explicit choice.

The shipped default is `Built by TangleClaw (Project: {project})`. The setting surface states that
changes appear only when each eligible file is naturally regenerated.

### 2. Eligibility is an explicit ownership registry

The first release supports only these private, per-project, wholly generated text surfaces:

- `.tangleclaw/session-prime.md`;
- `.tangleclaw/session-reentry.md`;
- `.tangleclaw/ui-wrap-advisory.md`;
- `.codex.yaml`, while it is untracked; and
- `.aider.conf.yml`, while it is untracked.

Callers pass an explicit frozen `surfaceId` to the provenance writer. The registry maps that ID to
syntax, placement and eligibility. It does not infer ownership from a file extension, a broad path
pattern, or the fact that TangleClaw happened to write the file.

Tracked carriers are ineligible. The same shared tracked-carrier predicate decides both insertion
and removal: when an eligible private carrier later becomes tracked, its next natural regeneration
removes an existing provenance line. This is a paired-state rule under ADR 0001.

Excluded from the first release are whole-file `CLAUDE.md`, all managed-block carriers (including
inside TangleClaw's block), git hooks, Master files, inactive notices, seeded/user-owned files,
third-party or vendor material, binaries, JSON, runtime state, logs, secrets, Caddy integrity
headers, plists and installer-owned system files. Existing ownership markers remain unchanged.

### 3. One renderer and writer own the format

`lib/provenance.js` is a leaf module containing the frozen registry, comment renderers, template
resolution, pure idempotent application and the shared atomic file writer. A registered writer
supplies a `surfaceId`, content and context. Repeated generation produces exactly one sentinel line;
changing the template replaces it; disabling the setting or losing eligibility removes it.

The sentinel is distinct from every ownership marker: `tangleclaw:provenance`. Templates cannot
emit that sentinel or any reserved ownership marker. A provenance line never changes the location
or meaning of an existing header, shebang, managed-block delimiter or integrity stamp.

### 4. Templates are bounded data, not source text

The override is at most 120 characters and may contain only `{project}` and `{engine}`. Unknown
tokens, control characters, newlines, comment terminators and reserved marker text are refused.
`{version}`, host names, filesystem paths, machine/session/project ids and credentials are excluded.
An explicit human-readable instance label may be designed later; the first release never infers one
from the machine.

Substituted values receive the same one-line, syntax-safe treatment as literal template text.
Adversarial project or engine names cannot terminate a comment, add a line or manufacture a marker.
Validation and rendering tests cover those values for every supported comment syntax.

### 5. Existing API reachability is not widened into agent authority

The project settings API carries the bounded value under its existing local threat model. This
feature adds no `tc` mutation command and no claim that an agent is authorized to change the owner’s
preference. The dashboard is the operator-facing control. A general caller-authentication boundary
for configuration APIs is a separate system concern; #1885 neither solves it narrowly nor treats
its absence as permission for autonomous changes.

Read-only capability reporting may state whether the feature is enabled and which surfaces are
eligible. It must not expose an absolute path or offer a mutation action.

### 6. Migration is lazy and explicit

Enabling, disabling or editing the setting performs no fleet sweep. Each eligible file gains,
updates or loses its line only during its next natural regeneration. The UI and documentation state
that propagation is gradual. Existing committed files are never dirtied merely because the setting
changed.

## Consequences

- Provenance cannot be confused with permission to overwrite a file.
- The feature remains byte-neutral while disabled.
- Projects opt in independently, avoiding fleet-wide churn and allowing clean-file projects to stay
  clean.
- The first slice is deliberately small. Adding a surface requires an ownership classification,
  format/placement rule, downstream-consumer audit and an explicit registry addition with tests.
- Supporting a new placeholder or a global default is a contract change, not a free-form template
  tweak.

## Rejected alternatives

- **Global-only setting:** overrides the per-project ownership preference and makes one opt-in touch
  every project as its files regenerate.
- **Stamp every TangleClaw write:** confuses writing with ownership and reaches user files, state and
  machine-readable formats.
- **Path or extension inference:** silently widens eligibility when layouts change.
- **Watermark inside managed blocks:** adds no useful ownership signal beyond the block markers and
  creates committed churn.
- **Stamp committed carriers without the project name:** avoids one #1619 violation but does not
  provide the provenance the feature exists for.
- **Immediate migration sweep:** creates unrelated diffs across the fleet and makes disabling the
  option unexpectedly destructive.

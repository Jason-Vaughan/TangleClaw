## Store upgrade rehearsal

On 2026-10-27, the live `~/.tangleclaw/tangleclaw.db` was opened read-only and copied through SQLite's backup API to a private scratch directory under `/tmp`. Only the copy was opened by this candidate's `lib/store.js` (`_setBasePath`, `init`, `close`) with `TANGLECLAW_HOME` pointing at the scratch directory. No server or session was started on the copy. The copy was opened a second time to check idempotence and then deleted. The live store was not migrated or otherwise written.

| Copy state | Main schema | `quick_check` | Foreign-key violations | Bridge route rows | Bridge outbound rows | `surface_kind` columns |
| :--- | ---: | :--- | :--- | ---: | ---: | :--- |
| Before candidate code | 68 | ok | 3 in `activity_log` | 78 | 530 | absent |
| After candidate code | 70 | ok | Same 3 in `activity_log` | 78 | 530 | present on both tables |

The second open left the inspected schema, row counts and checks unchanged. The three `activity_log` foreign-key violations were already present in the copied live store before migration and were not added by it; they remain an existing data finding for release review. The merged code's `CURRENT_SCHEMA_VERSION` is **70** (v68→v69 and v69→v70); there is no v71 migration in this candidate. Scoped permission-request tables are created lazily by their owning module on use, so a store-only `init()` rehearsal does not claim to have exercised that route.

## Rollback and limits

Before any live update, preserve and verify a consistent pre-update backup and an independently operable recovery path. A rollback needs separate Operator authorization. This rehearsal tested store initialization on a copy; it did not test a full server launch, Discord delivery, a backup restore, or browser interaction on the live install.

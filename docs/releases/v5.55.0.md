# v5.55.0 — Checkout ownership and the live install

This release candidate reconciles the five closed issues in Milestone #40. The [release status](v5.55.0-status.md) tracks the code merge, tag, GitHub Release, local update, and live verification separately.

- A dry-run-first CLI plans retirement of clean, inactive worktrees and safe `[gone]` branches, and rechecks targets before applying changes (#1267).
- Server freshness remains tied to the checkout whose code actually runs. Coupling diagnostics identify linked worktrees and declared dedicated roots; an operator can use a CLI to provision a dedicated checkout and repoint a validated launchd plist (#1672).
- Stale-install response helpers classify upstream changes and can fast-forward only a verified records-only delta on a clean `main` checkout with no wrap in flight. Executable or mixed changes yield an operator-coordinated restart decision. This standalone core logic lives in `lib/checkout-freshness.js` and `lib/update-applier.js`; no live route or poller invokes it yet (#1710).
- `lib/checkout-ownership.js` provides standalone deterministic worktree ownership and write-admission module APIs. Its callable helpers are ready for host integration; live command and write paths do not invoke them yet (#1332).
- `lib/branch-ownership.js` provides standalone deterministic branch ownership, review-evidence invalidation, and mutation-guard module APIs. Its callable helpers are ready for host integration; live command, write, and push paths do not invoke them yet (#1977).

The dated [5.55.0] section of `CHANGELOG.md` compiles and consumes the five accepted release fragments.

# v6.3.0 — A workspace mode bar and wizard launcher, live sprint routes, the running engine on member badges, and a Medusa registry cache

TangleClaw v6.3.0 is a minor release on top of v6.2.10. The v6 shell gains a workspace mode bar and a wizard launcher that works with a chat open, and the live server now serves the sprint wave board and sprint reports. A member's badge shows the engine it is really running, and Medusa stops re-reading every project's registry on every message.

## Added

- **Workspace mode bar and wizard launcher** (#3086; tests in `test/v6-b1-ui-shell.test.js` and `test/v6-browser-shell-and-conversation-e2e.test.js`): tabs at the top of the main view switch between Chat, Sprint & Cars, Charter & Roadmap, Kaizen & Reports and Wizard. The arrow keys, Home and End move between them, opening a project or member always lands in Chat, and switching modes leaves the chat, its draft and its scroll as they were. A "+ New Project / Fleet Wizard" button in the sidebar and a "+ New" button beside the tabs open the template wizard at any time. Sprint & Cars shows the dispatch board, Charter & Roadmap the planned waves, and Kaizen & Reports the current sprint's report. They are drawn by the sprint UI module when it loads and by an escaped built-in list otherwise, and a server that does not serve those routes yet says so.
- **Live sprint routes** (#3087; tests in `test/native-sprint-tracker.test.js`): `GET /api/sprint-waves` shows the current sprint's waves and where each car stands, from the v6 wave scheduler's saved runs. `GET /api/sprint-reports/current` (or `/<version>`) answers that sprint's report summary; anything that is not `current` or a version is refused with `400`. `POST /api/sprint-waves/validate-disjointness` checks a set of cars for shared files. `POST /api/sprint-waves/sync` is the operator's or the Master's only, and answers `NOT_CONFIGURED` until a roadmap source is set up. The sprint UI module gains Charter readiness and Kaizen ledger panels that escape everything they show and link only to `http(s)` addresses, and the service worker always fetches it fresh.
- **The running engine on member badges** (#3094; tests in `test/projects.test.js` and the shell tests): the projects API reports the engine of a member's running session, even when its terminal could not be read, and of its most recent session. The v6 badge picks the running engine first, then the last one used, then the configured one, and names the model in its tooltip. A store that cannot be read leaves the badge empty and still lists the project.

## Fixed

- **Medusa registry cache and unreadable registries** (#3084; tests in `test/api-medusa.test.js`): Medusa keeps each project's workspace registry in memory until its file changes, instead of re-reading every registry on every message and roster read. A registry that cannot be read (for example, because macOS privacy controls block the folder) is treated as unreadable, never as empty. A send or broadcast refused as cross-fleet then names the unreadable registries of projects in the sender's own fleet (`details.reason: REGISTRY_UNREADABLE`), since a recipient may really be in that fleet; it is still refused. Registries of other fleets' projects are never named to the sender, so a refusal does not reveal another fleet's projects.

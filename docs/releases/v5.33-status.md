## The release's name against what it delivers

The release is named "Newer Codex versions". **It does not make any newer Codex version launchable or wakeable.** Codex 0.156.1 remains the only version launched on the native channel and woken.

Run signed in on 2026-10-12, Codex 0.161.0 and 0.162.0 each launched and were held correctly while an answer streamed. Once Codex reported the answer finished, TangleClaw typed its mail notice into a pane that had not finished drawing. A wake that types into a pane it cannot read as ready is the fault #2059 reports, so neither version was listed. The Operator moved #2059 and #2222 to v5.34 on 2026-10-12 ("2059 next", "2222 next"), where a revised gate is to be built, proved signed in and accepted by the Architect.

What this release does deliver toward them: the settling hold, the launch gate, each version's screens captured and declared, and the reason they stay unlisted pinned in a test.

## After the upgrade, the operator must

- **Add two fields to a Codex engine profile of your own** (#2187). A profile that uses the Codex adapter must declare `capabilities.wake.headerPattern` and `startingPattern`. The bundled profile does. Without them the trust-free startup fire is held as `pane_not_ready`, naming the two fields.
- **Nothing else.** The Discord helper needs no restart for this release. An upgrade turns no override on, and no merge queue exists until the Operator makes one.

## Upgrade rehearsal

Run on 2026-10-13 at 15:06 PDT, in isolation, at commit `299967d5`, at the asking of the Architect and the ProjectManager before either authorized the deploy.

The live store was copied with `sqlite3 .backup` into a scratch directory and the copy opened by that commit's own `lib/store.js` with its base path set to that directory. The live server, its database and its log were not touched.

| Store copied | Schema before | Schema after | Integrity | Foreign-key violations | Bridge schema problems | Tables lost | Row counts changed |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| The live store, copied at the rehearsal (67 tables, 303,394 rows) | 63 | 66 | ok | 0 | none | none | only `schema_version` |

Six tables were added, each empty. Opening the upgraded copy a second time changed nothing. Three minutes later the same upgrade ran on the live store itself at the deploy, and it read schema 66 with integrity ok.

**Why no server was started on a copy.** A TangleClaw server started on a copy of the live store would read the live sessions from it, connect to the switchboard under their identities and run its monitors against the real tmux panes of this host. Both authorizers accepted the store's own start in its place.

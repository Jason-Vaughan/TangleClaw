## Confidence check

1. **Problem.** A wrap blocks and asks Include or Leave about files TangleClaw wrote, not the operator. Once a TangleClaw edit misses one commit (for example the managed block rewritten at launch), the file is "already uncommitted at launch" on every later session, so the wrap asks about it forever. The 2026-09-15 scan found this in most of 36 projects.
2. **Success.**
   - A wrap on a tree where only TangleClaw files are dirty commits nothing it shouldn't and asks nothing.
   - A managed-block change is committed and named in the summary.
   - The operator's own edits, including one line outside the markers, are still asked about exactly as today.
3. **Out of scope.**
   - Moving state out of tracked files (Chunk 02, #1510).
   - Heal on launch (#1511).
   - Un-tracking offer (#1512).
   - The secret check (#1513).
   - Any `public/` change: the drawer row text comes from the step's `detail`.
   - `.claude/.gitignore` appends. Proving them needs a line-diff rule nobody has ratified, so they stay normal classification. Recorded, not dropped.

## Design

A new module, `lib/wrap-steps/_tc-owned-paths.js`, is the single source of truth. For one dirty entry it answers `'state' | 'maintenance' | null`.

- **`state`**: the path matches the machine-state registry. **Never asked, never staged.** It is reported as a count ("N TangleClaw state files left uncommitted").
  - [ASSUMPTION: leave rather than commit.] Committing volatile state makes churn commits and can put session transcripts and uploads (`continuity/sessions/*/uploads`) into project history. Chunk 02 takes these files out of tracking. Veto → they become `maintenance` instead.
- **`maintenance`**: a tracked file whose delta is provably TangleClaw's. **Staged without asking**, and listed by name in the step output and the commit body.
  1. *Managed-block carrier*: any tracked path equal to an engine profile's `configFormat.filename` or a shared convention carrier, with a markers syntax. Maintenance when both HEAD and the working copy hold exactly one well-formed block and the text outside the block is byte-identical. The proof is lifted from `update-applier` into `lib/managed-block.js` (`outsideManagedBlock`, `regionOnlyDiff(head, work, markers)`), and update-applier calls the shared copy so there is one proof. Engine-agnostic: every profile's filename is checked, never a literal `CLAUDE.md`.
  2. *Shared hook settings* (`.claude/settings.json` via `SHARED_SETTINGS_BASENAME`): both sides parse as JSON and are deep-equal after removing every hook entry `_isTangleClawHookEntry` recognises (and hook-event arrays left empty by that removal).
  3. *`.tangleclaw/project.json`*: both sides parse as objects. Every top-level key that differs is `lastWrapSha`, a migration-owned key, or a key absent from HEAD whose working value deep-equals `DEFAULT_PROJECT_CONFIG[key]`. If `lastWrapSha` is the ONLY difference, the file is `state`, not `maintenance`.
- **`null`**: everything else, including every read or parse failure. The path goes through today's classification unchanged, so every failure resolves to asking, the safe answer.

`classify` consults the module **before** the launch-dirty check, since that check is what makes the question repeat. Its return gains `tangleclawState: string[]` and `tangleclawMaintenance: string[]`, and `stageable` becomes `owned + included + maintenance`. `owned`/`foreign`/`undecided` keep their meaning and just stop containing TangleClaw's paths.

- Both callers pass nothing new; `classify` reads HEAD itself (argv `git show HEAD:<path>` via a sync seam, cwd = `scope.workToplevel`). Only paths matching the candidate registry are read, so the cost is a handful of `git show` calls per wrap.
- A deletion is `state` when its path is in the state registry, otherwise `null`.
- Fail-closed logging: every `null` for a candidate path logs one info line with the reason (the update-applier convention), so "why did it ask about CLAUDE.md" is answerable from the log.

**Contract surface:** `classify`'s return shape gains two fields and `stageable` widens. Consumers:
- `session-files.js` (`ownedCount`, `detail`)
- `commit.js` (`stageable`, the `skipped` branch on empty `stageable`, commit body)
- `wrap-drawer` / `public/session.js`, which read the step output (additive fields only; verify before merge)

## Tests (real git in temp repos; never the live store)

- `test/wrap-tc-owned-paths.test.js`:
  - state registry hits and misses (`plans/`, `memories/` and `priming/` are NOT state);
  - managed-block-only diff → maintenance for `CLAUDE.md` AND `AGENTS.md`;
  - one operator line outside the markers → null;
  - duplicated or missing markers → null;
  - a file absent from HEAD → null;
  - a whole-file generated `.codex.yaml` → null;
  - settings.json with only TangleClaw hook entries removed → maintenance, plus an operator permission added → null;
  - project.json with only `lastWrapSha` → state, defaults added → maintenance, `activePlan` changed → null, invalid JSON → null.
- `test/wrap-file-ownership.test.js` additions, all through `classify` with a launch baseline that marks the files dirty-at-launch (the repeating case):
  - a TangleClaw-only tree has zero undecided;
  - maintenance is stageable;
  - state is not stageable;
  - an operator file is still undecided.
- A multi-hop case: session-files and then commit, on the same tree, agree (no block, same stageable set).
- The existing update-applier suites stay green unchanged, since the proof moves but its behavior doesn't.

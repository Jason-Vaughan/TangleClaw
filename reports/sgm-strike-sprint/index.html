🧠 Architectural Deep-Dive — Persistent Agent Memory: TangleClaw Continuity Protocol vs. sqlite-graph-memory Collaboration & Integration Blueprint

How TangleClaw Handles Cross-Session State Today — And Why sqlite-graph-memory Is the Missing Retrieval Layer

One of our primary reasons for running a full strike sprint on tonydzi/sqlite-graph-memory was to evaluate its architecture against TangleClaw’s own cross-session state management. Both systems share a core engineering philosophy: stdlib SQLite, plain Markdown files on disk, zero heavy graph databases (no Neo4j/ETL), and zero LLM token tax on every turn. Yet they solve complementary halves of the persistent memory problem:

1. How TangleClaw Runtime & Rules Handle Memory Today (The Continuity Capsule)

TangleClaw is a multi-engine orchestrator managing 10 to 16 concurrent AI sessions across Claude Code, Codex, and Antigravity. When a session’s context window fills up or an engine rotates, TangleClaw relies on a deterministic, generation-bound handoff rather than semantic retrieval:

  • Generation-Bound Continuity Capsules (tc rotation & tc start): Before a session clears or wraps, it writes a structured Continuity Capsule bound to its launch generation. When the replacement session starts, it runs a mandatory 4-step attestation sequence (tc start next → governance, state, task → tc start ready) that proves the new session read its charter, active branch/commit freshness, and exact next action before taking a single turn.
  • Durable SQLite Session Rules & 2-Day Learnings Loop: At session wrap, agents append dated ## YYYY-MM-DD — <title> entries to .tangleclaw/memories/learnings.md. When TangleClaw’s SQLite store observes the same learning pattern across two distinct days, it auto-proposes a durable session-rule (status='proposed' → operator-ratified active) that is injected into future session primes.
  • Self-Deleting Bridge Memos (MEMORY.md Hygiene): Temporary cross-session notes (in-flight migrations, chat-ratified rulings not yet in a PR) must carry an explicit mechanical Auto-cleanup check in frontmatter so the next session verifies whether the bridging condition resolved and deletes the memo + prunes MEMORY.md—preventing stale memos from accreting into false canon.

2. Why sqlite-graph-memory Is a Better Way to Handle Long-Horizon Recall

TangleClaw’s Continuity Capsule excels at immediate generation N → N+1 task continuity, and session-rules excel at global standing invariants. Where TangleClaw’s current model hits a wall is mid-granularity associative recall across hundreds of historical plans (.tangleclaw/plans/archive/), sprint post-mortems, ADRs, and multi-week debugging notes:

  • Injecting Everything Blows Context; Static Rules Miss Local Context: You cannot inject 60 archived sprint plans into every prime, and keyword grep misses semantic paraphrases or 2-hop architectural links (e.g., an issue touching injectCommand whose root cause sits in a note linked via [[AskUserQuestion-TUI-State]]).
  • Why sqlite-graph-memory’s 4-Stage Pipeline Wins:
    1. Dense Entry Points (e5-base + Incremental Index #17): Fast semantic entry into `.tangleclaw/plans/` and `.tangleclaw/memories/` with sub-second incremental updates after each wrap.
    2. Query-Time 1-Hop [[wikilink]] Expansion + Entity Gate (looks_like_entity): Follows hand-curated [[plan]], [[issue]], and [[ADR]] links directly from the markdown files at query time (zero SQL edge-table sync drift) while suppressing graph noise on narrow symbol/entity queries.
    3. Cross-Encoder Rerank + Honest --ab Telemetry: Compresses the expanded pool back to top-12 and logs every vector-vs-graph delta to SQLite (ab_recall) so graph expansion has to prove it helped on our corpus.
    4. Zero-Token Stop-Hook Ledger (turnstate_hook.py): Matches TangleClaw’s zero-token-overhead rule while capturing per-turn tool/file trajectories in standard SQLite.

Because sqlite-graph-memory is an external repository not yet on the remote Testament coordinator’s allowlist (tls://testament-wire.rodeo.illuminati.org:443), our lanes used an ephemeral untracked .testament.toml (listed in .git/info/exclude and removed prior to commit) to execute pytest under Testament’s local admission-cap fallback, generating verifiable request_id receipts (4c49c847, 622e427b, f8e65b9f, 3d8bbe35, d2fd0a60) with zero git pollution.

What Didn't Work & Proven Fixes — TangleClaw Fleet Improvement Suggestions

1. Master Authority Split Between `PATCH /api/config` and `GET /api/master/authority` (Filed as Issue #2823)

Setting master.accessLevel = "write" via PATCH /api/config updated config.json, but GET /api/master/authority still reported toggleState: "read-only" (effectiveRole: "observer") because applyOperatorAuthorityChange() was only wired to POST /api/master/authority. Fix / Guardrail: Filed Jason-Vaughan/TangleClaw#2823 (roadmapped to Milestone #46 v5.61.0) to unify both endpoints onto a single authority state transition.

2. Session-Lifecycle Guards (`#2129`, `#2402`) Blocked Autonomous PMs From Launching/Clearing Their Fleet (Filed as Issue #2824)

When SGM-PM called POST /api/sessions/SGM-Arc-PRR to launch its 4 child lanes autonomously, the server returned 403 SESSION_LIFECYCLE_FORBIDDEN because #2129 restricted session launch/clear/wrap exclusively to OPERATOR or MASTER. Fix / Rule: Filed Jason-Vaughan/TangleClaw#2824 (roadmapped to Milestone #43 v5.58.0) to grant verified Coordinator/PM sessions scoped lifecycle authority (launch, /clear, /wrap, and POST /api/sessions/:project/command) over lanes in their own project group.

3. Missing Auto-Bootstrapped Project Group & Stale `~/.tangleclaw/cli/bin/tc` Binary for New Strike Fleets (Filed as Issue #2825)

Section 01 · Architectural Deep-Dive

How v5.47.0 Hardens Engine Startup Dialogs, Selector-Row Guards & Sandbox Diagnostics

Engine CLIs draw interactive prompts before or during a session where a blind keystroke can terminate the session or select an unintended option. Sprint v5.47.0 unifies startup-dialog schema validation and classification across Claude Code and Codex, closes the partial shared-option race between folder trust and bypass-permissions confirmation, adds positive selector-row refusal for mid-session injections, introduces a strictly re-verified per-project opt-in for folder trust, and surfaces restarts and sandbox loopback blocks directly in launch readiness.

PILLAR 01 · UNIFIED DIALOG READER, BYPASS-PERMISSIONS & SELECTOR GUARD (#2221, #2205, #2219)

Single Validator, Partial-Frame Suspect Hold & Positive Selector-Row Refusal

In W1-A (PR #2711), lib/launch-dialog-guard.js#read was converged onto lib/startup-dialog.js#entryErrors and the shared pane classifier (#2221), eliminating duplicate dialog-schema parsing while adding validated acceptKeys (non-empty array of allowed key tokens) to data/engines/claude.json. For #2205, Claude Code now declares bypass_permissions_confirm separately from trust_required. Because both screens share the default "No, exit" option, a half-rendered frame showing only "No, exit" is withheld under the neutral startup_screen_suspect code rather than misattributing to folder trust, and glyph-qualified prompt detection prevents option prose (e.g., "2. No, exit") from spoofing the composer boundary. In W2-A (PR #2713, #2219), lib/startup-dialog.js#_promptRow and lib/startup-dialog.js#withholdFor distinguish a positively observed selector option row (selectorRow: true) from an ambiguous noncomposer frame: any mid-session command or switchboard wake against a live selector row is refused with pane_not_at_prompt (HTTP 409 STARTUP_DIALOG), whereas a located composer draft retains its save-clear-send-restore path.

PILLAR 02 · PER-PROJECT OPT-IN FOLDER TRUST WITH PER-KEY RE-VERIFICATION (#2168)

Default-Off acceptFolderTrust, Staggered Keys & Activity Audit Trail

Building on W1-A and W2-A, W2-B (PR #2712, #2168) introduced the per-project acceptFolderTrust boolean setting (default false) in lib/project-config.js, lib/projects.js, public/index.html, and public/ui.js. During launch, lib/sessions.js#_acceptsFolderTrust checks whether the project explicitly opted in and whether the live pane positively matches the engine’s trust_required dialog with a valid declared acceptKeys sequence (["Down", "Enter"] for Claude Code). Before sending each individual key across the staggered key timer, stillOurs() re-verifies that the live session row still belongs to the same launch (treating a store read throw as "not ours") and re-reads the tmux pane to confirm the exact same trust_required dialog is still on screen. Only after every key in acceptKeys is delivered does TangleClaw record launch.folder_trust_accepted in project activity with the project, directory, session, and dialog id. TangleClaw never writes an engine’s trust state file directly, and all other startup dialogs remain operator decisions.

PILLAR 03 · CODEX LOOPBACK SANDBOX DIAGNOSIS & RESTART DROP RECOVERY (#1836, #2193)

Actionable Full-Auto Unready Notes & Deferred First-Turn Accounting

In W1-B (PR #2709, #1836), data/engines/codex.json declares that Codex’s fullAuto mode (--full-auto / --sandbox workspace-write) blocks outbound and loopback network access by default. When a Codex fullAuto launch sequence becomes unready with zero HTTP pulls recorded, lib/startup-control-codex.js#loopbackSandboxNote and lib/launch-sequence.js#_loopbackSandboxNote attach a structured likely-cause note and remedy (enable sandbox_workspace_write.network_access = true in ~/.codex/config.toml or switch launch mode), surfaced in both the API and tc start status (lib/tc-verbs.js). In W1-C (PR #2710, #2193), lib/sessions.js#reconcileDeferredFirstTurnsOnRestart tracks pasteOwed and kickoffOwed alongside hasSequence so a server restart that interrupts a first turn waiting behind a startup dialog records firstTurnDroppedOnRestart on the session (including no-rules and silent-prime launches) while ensuring a dialog that appears after the first turn was already delivered never creates a false drop.

⚠️ What Didn't Work & Proven Fixes (Process & Tooling Friction)

1. Upstream Claude Quota Cap Mid-Wave on Single-Engine Builder Lanes

TC-Lane-C (Claude Opus 4.7) hit an account/window rate limit at 17:45Z right as W2-B PR #2712 needed its final ancestor sync. Although A483-R12 recovered in 18m via TC-Lane-D (Codex gpt-6-sol high), homogeneous engine assignment across Builders creates correlated quota risk. Fix / Guardrail (P38): Balance Builder engines across claude and codex (`gpt-6-sol high`) at batch kickoff and pre-authorize hot-spare ancestor-sync failover in the base charter.

2. Rebased Release PR vs. Next-Sprint Wave 1 Fragments in changelog.d/ (#1220)

When a prior sprint’s release PR (`v5.46.1 PR #2708`) is rebased onto `main` after the next sprint’s Wave 1 PRs have already merged their `changelog.d/*.md` fragments to `main`, `node scripts/release-prepare.js` (`#1220`) rightly refuses to run if any fragment remains in `changelog.d/`. Fix / Guardrail (P39): Cut `W-REL` before merging the next sprint’s Wave 1 PRs to `main`, or explicitly run `node scripts/release-prepare.js` as a mandatory pre-PRR check after any release-branch rebase.

3. Unstaged package-lock.json Dirtying Builder Working Trees (TC-Lane-B)

During `W1-A` and `W2-A`, `TC-Lane-B`’s working tree accumulated an unstaged `M package-lock.json` modification that caused `tc freshness` to report `1 dirty` after branch merge until cleaned during wrap/re-prep. Fix / Guardrail (P40): Add a pre-PR / post-merge `git checkout -- package-lock.json` check whenever `package.json` is untouched so incidental npm lockfile touches never dirty a lane.

4. 3–4 Review Rounds on State-Machine PRs Due to Implicit Sub-Invariants

`W1-C (#2710)`, `W1-A (#2711)`, and `W2-B (#2712)` each took 4 review rounds (`107m–196m` open-to-merge) because subtle negative invariants (e.g., *"what if a dialog appears AFTER the first turn was delivered?"* or *"what if the dialog disappears between key 1 and key 2 of acceptKeys?"*) were discovered iteratively in review rather than enumerated in the pre-dispatch brief. Fix / Guardrail (P41): Include a 3-bullet *"Negative & Mid-Transition Invariants"* checklist in `TC-Lane-Arc`’s pre-dispatch lane brief for state-machine issues.
